# Project Brain

Project Brain is a lightweight context-orchestration layer for coding agents such as Codex and Claude Code. It keeps persistent project memory outside the chat session, compiles only relevant context for each task, tracks development intent and semantic change batches, and routes cheap work to a local Ollama model.

## Why

Large context windows are not a reason to resend an entire repository on every turn. Project Brain treats the repository as durable indexed knowledge and produces a small task-specific context packet.

The core loop is:

```text
user task
   -> incremental repository index
   -> persistent intent
   -> relevant context compilation
   -> strong-model controller
       -> local worker for bounded cheap work
       -> strong model for risky/complex work
   -> semantic change batches
   -> verification
   -> documentation drift check
   -> compact persistent memory / handoff
```

## MVP features

- Incremental SHA-256 repository index. Unchanged files are reused instead of reprocessed.
- Symbol/import extraction for lightweight relevance ranking.
- Token-budgeted Context Compiler.
- Persistent intents and semantic change batches.
- Complexity-based router with mandatory strong-model escalation for security, DB migrations, breaking APIs, production incidents, and architecture decisions.
- Strong-model delegation planner that accounts for orchestration overhead before spawning local work.
- Local Ollama worker, defaulting to `qwen3.5:4b`.
- Context capsules generated by the local model.
- Session Handoff capsules for restarting with compact state instead of chat history.
- Project-memory bootstrap and documentation drift suggestions.
- Thin `AGENTS.md` and `CLAUDE.md` adapters so the canonical memory remains `.project-brain/`.
- Zero runtime Python dependencies. `pytest` is only required for development.

## Install

Requires Python 3.11+ and optionally Ollama for local context work.

```bash
pip install -e .
```

For development:

```bash
pip install -e '.[dev]'
pytest -q
```

For the local worker:

```bash
ollama pull qwen3.5:4b
ollama serve
```

## Initialize any project

```bash
cd /path/to/project
brain init
```

This creates persistent project memory under `.project-brain/`, including intents, batches, capsules, architecture notes, summaries, state and handoffs.

## Typical development flow

### 1. Incremental warm-up

```bash
brain index
```

The first run indexes source/text files. Later runs compare SHA-256 hashes and only report changed/deleted files.

### 2. Ask who should do the work

Basic complexity routing:

```bash
brain route "update login button copy and tests"
```

Controller/worker delegation economics:

```bash
brain delegate "summarize changed authentication files for documentation"
```

A delegation result includes the controller, local worker, expected strong-model token saving, estimated latency delta and verification rule.

The strong model remains the planner and final reviewer. Local delegation is intended for bounded work such as summaries, extraction, classification, documentation, formatting, simple tests and other outputs that can be checked cheaply. Security, architecture, production incidents, risky migrations and breaking changes remain strong-model work.

### 3. Create persistent intent

```bash
brain intent-create "Refresh token rotation" \
  --goal "Prevent refresh-token replay" \
  --success "A refresh token can be used once" \
  --constraint "No breaking client API" \
  --affected auth \
  --affected users \
  --verify "integration tests"
```

### 4. Split work into semantic batches

```bash
brain batch-create INT-... "domain rules" --scope auth
brain batch-create INT-... "integration tests" --scope tests
```

### 5. Build local Context Capsules

```bash
brain capsule src/auth/service.py
```

### 6. Compile context instead of loading the repository

```bash
brain context "implement refresh token reuse detection"
brain context "implement refresh token reuse detection" --explain
```

The compiler prefers project memory, active intents, architecture and relevant capsules. Raw source is loaded only when required.

### 7. Hand off before a session becomes bloated

Check the current session estimate:

```bash
brain handoff-check "continue refresh token rotation" --current-tokens 22000
```

Create a compact continuation capsule:

```bash
brain handoff "continue refresh token rotation" \
  --current-tokens 22000 \
  --note "integration tests are green"
```

The new session should load the handoff, active intent and relevant capsules rather than replaying the old conversation.

### 8. Check documentation drift

```bash
brain drift
```

### 9. Close the intent

```bash
brain intent-close INT-...
```

## Context policy

```text
HOT
  active intent
  current batch
  current diff

WARM
  affected module capsules
  relevant ADRs
  relevant prior batches

COLD
  project/module summaries
  historical batches

ARCHIVE
  raw conversations/logs
```

A strong model should normally receive HOT plus selected WARM context, not the whole repository. The default task-context target is 30K tokens even if a local model supports a much larger window.

## Controller / worker model

The preferred execution pattern is:

```text
strong model
  PLAN
    |
    +--> tiny/bounded subtask --> local Qwen --> compact evidence
    |                                      |
    +--------------------------------------+
                    VERIFY
                      |
                 next decision
```

Delegation is skipped when orchestration overhead is expected to consume most of the token saving. The controller therefore avoids spawning a local call for trivial one-line work.

Default configurable assumptions:

```json
{
  "delegation_overhead_tokens": 450,
  "min_delegation_token_saving": 500,
  "estimated_local_task_seconds": 8.0,
  "estimated_strong_task_seconds": 3.0,
  "handoff_context_threshold": 0.72
}
```

These timing values are calibration placeholders, not benchmark claims. Measure them on the actual local hardware and provider, then update the config.

## Model routing

Project Brain scores scope, ambiguity, architecture impact, security impact, cross-module impact, irreversibility and unknown code.

```text
0..7   -> local Ollama worker
8..14  -> local attempt, verification, strong-model fallback allowed
15+    -> strong coding model
```

Critical flags bypass the score and go directly to the strong model.

## Configuration

After `brain init`, edit `.project-brain/config.json`:

```json
{
  "ollama_url": "http://127.0.0.1:11434",
  "local_model": "qwen3.5:4b",
  "target_context_tokens": 30000,
  "max_local_complexity": 7,
  "local_then_escalate_complexity": 14,
  "delegation_overhead_tokens": 450,
  "min_delegation_token_saving": 500,
  "estimated_local_task_seconds": 8.0,
  "estimated_strong_task_seconds": 3.0,
  "handoff_context_threshold": 0.72
}
```

The strong model is provider-independent. Codex, Claude Code, another agent, or a future provider can consume the compiled context and use Project Brain as persistent engineering memory.
