# Project Brain

Project Brain is a lightweight context-orchestration layer for coding agents such as Codex and Claude Code. It keeps persistent project memory outside the chat session, compiles only relevant context for each task, tracks development intent and semantic change batches, and routes cheap work to a local Ollama model.

## Why

Large context windows are not a reason to resend an entire repository on every turn. Project Brain treats the repository as durable indexed knowledge and produces a small task-specific context packet.

The core loop is:

```text
user task
   -> incremental repository index
   -> persistent intent
   -> relevant context compilation
   -> strong-model controller
       -> local worker pool for bounded cheap work
       -> strong model for risky/complex work
   -> selective strong-model verification
   -> telemetry / adaptive routing
   -> semantic change batches
   -> documentation drift check
   -> compact persistent memory / handoff
```

## Features

- Incremental SHA-256 repository index. Unchanged files are reused instead of reprocessed.
- Symbol/import extraction for lightweight relevance ranking.
- Token-budgeted Context Compiler.
- Persistent intents and semantic change batches.
- Complexity routing with mandatory strong-model escalation for security, DB migrations, breaking APIs, production incidents, and architecture decisions.
- Strong-model delegation planner that includes orchestration overhead.
- Parallel local Ollama worker pool, defaulting to `qwen3.5:4b`.
- JSONL telemetry for latency, token estimates, errors, fallbacks, and strong-model acceptance.
- Adaptive routing policy that expands or shrinks local delegation after enough real samples.
- Context capsules generated by the local model.
- Session Handoff capsules for restarting with compact state instead of chat history.
- Project-memory bootstrap and documentation drift suggestions.
- Thin `AGENTS.md` and `CLAUDE.md` adapters so canonical memory remains `.project-brain/`.
- Zero runtime Python dependencies. `pytest` is only required for development.

## Install

Requires Python 3.11+ and optionally Ollama for local context work.

```bash
pip install -e .
```

For development:

```bash
pip install -e '.[dev]'
pytest -q
```

For the local worker:

```bash
ollama pull qwen3.5:4b
ollama serve
```

## Initialize any project

```bash
cd /path/to/project
brain init
```

This creates persistent project memory under `.project-brain/`, including intents, batches, capsules, architecture notes, summaries, state, telemetry and handoffs.

## Typical development flow

### 1. Incremental warm-up

```bash
brain index
```

### 2. Ask who should do the work

```bash
brain route "update login button copy and tests"
brain delegate "summarize changed authentication files for documentation"
```

`brain delegate` reports the controller, worker, expected strong-model token saving, estimated latency delta, adaptive multiplier, and verification rule.

### 3. Execute bounded work locally

One task:

```bash
brain worker-run --task "summarize changed auth files"
```

Parallel tasks:

```bash
brain worker-run \
  --task '{"task":"summarize backend diff","task_type":"summary","context":"..."}' \
  --task '{"task":"classify documentation drift","task_type":"documentation","context":"..."}' \
  --task '{"task":"summarize test failures","task_type":"test-log","context":"..."}' \
  --concurrency 2
```

Each result receives an `EXE-...` execution id and is written to `.project-brain/telemetry/executions.jsonl`.

The local worker contract is deliberately narrow:

```json
{
  "answer": "compact result",
  "evidence": ["paths, symbols, or concrete inputs"],
  "uncertainty": 0.1
}
```

The strong model should verify the evidence rather than re-reading everything the local worker already processed.

### 4. Record strong-model verification

After the strong controller reviews a worker result:

```bash
brain telemetry-mark EXE-abc123 accepted
```

or:

```bash
brain telemetry-mark EXE-abc123 rejected
```

Inspect learned performance:

```bash
brain telemetry
brain telemetry --tail 10
```

After `adaptive_min_samples` reviewed/observed runs, the policy adjusts the local delegation envelope. High acceptance can expand it; low acceptance or excessive local latency shrinks it.

### 5. Create persistent intent

```bash
brain intent-create "Refresh token rotation" \
  --goal "Prevent refresh-token replay" \
  --success "A refresh token can be used once" \
  --constraint "No breaking client API" \
  --affected auth \
  --affected users \
  --verify "integration tests"
```

### 6. Split work into semantic batches

```bash
brain batch-create INT-... "domain rules" --scope auth
brain batch-create INT-... "integration tests" --scope tests
```

### 7. Build local Context Capsules

```bash
brain capsule src/auth/service.py
```

### 8. Compile context instead of loading the repository

```bash
brain context "implement refresh token reuse detection"
brain context "implement refresh token reuse detection" --explain
```

### 9. Hand off before a session becomes bloated

```bash
brain handoff-check "continue refresh token rotation" --current-tokens 22000
brain handoff "continue refresh token rotation" \
  --current-tokens 22000 \
  --note "integration tests are green"
```

### 10. Check documentation drift and close

```bash
brain drift
brain intent-close INT-...
```

## Context policy

```text
HOT
  active intent
  current batch
  current diff

WARM
  affected module capsules
  relevant ADRs
  relevant prior batches

COLD
  project/module summaries
  historical batches

ARCHIVE
  raw conversations/logs
```

A strong model should normally receive HOT plus selected WARM context, not the whole repository. The default task-context target is 30K tokens even if the local model supports a much larger window.

## Controller / worker model

```text
                         STRONG MODEL
                       plan / decisions
                             |
             +---------------+---------------+
             |               |               |
             v               v               v
        local worker    local worker    local worker
          summary          tests            docs
             |               |               |
             +---------------+---------------+
                             |
                       evidence packets
                             |
                             v
                         STRONG MODEL
                      selective verification
                             |
                             v
                     accept / reject telemetry
```

Delegation is skipped when orchestration overhead is expected to consume most of the token saving. Critical-risk work bypasses local execution entirely.

## Adaptive routing

Telemetry tracks:

- execution id and task type
- model and route
- measured local latency
- estimated input/output tokens
- errors and fallbacks
- strong-model `accepted` / `rejected` verdicts

The initial thresholds are conservative. Once enough samples exist, `AdaptivePolicy` computes a multiplier:

```text
high acceptance + acceptable latency -> local envelope grows
low acceptance                       -> local envelope shrinks
high local latency                    -> local envelope shrinks
insufficient samples                  -> defaults stay unchanged
```

This is intentionally a bounded heuristic rather than self-modifying code. Configuration remains the hard safety boundary.

## Configuration

After `brain init`, edit `.project-brain/config.json`:

```json
{
  "ollama_url": "http://127.0.0.1:11434",
  "local_model": "qwen3.5:4b",
  "target_context_tokens": 30000,
  "max_local_complexity": 7,
  "local_then_escalate_complexity": 14,
  "delegation_overhead_tokens": 450,
  "min_delegation_token_saving": 500,
  "estimated_local_task_seconds": 8.0,
  "estimated_strong_task_seconds": 3.0,
  "handoff_context_threshold": 0.72,
  "local_worker_concurrency": 2,
  "local_worker_timeout_seconds": 180,
  "local_worker_num_ctx": 32768,
  "adaptive_min_samples": 20,
  "max_preferred_local_latency_seconds": 20.0
}
```

Start with local concurrency `1` or `2` on a single GPU. Increase only after measuring throughput and VRAM/RAM pressure. Parallel requests are useful only when the inference backend and hardware can actually overlap or batch them efficiently.

The strong model is provider-independent. Codex, Claude Code, another agent, or a future provider can consume compiled context and use Project Brain as persistent engineering memory.
